# COK 直连控制台(网页)

本地网页, 把直连能力的**监控**和**操作**都搬到浏览器里。
零新依赖(只用 Python 标准库), 复用 `cok_daemon.py` 的 watcher / extractor / 写操作实现。

## 启动

```bash
cd ~/workspace/me/cok/COK-CN1-analysis/protocol

python3 cok_web.py --account-device                 # 默认 127.0.0.1:8770
python3 cok_web.py --account-device --open           # 启动后自动开浏览器
python3 cok_web.py --account-device --port 9000 \
    --webhook <URL> --webhook-type wechat            # 告警
python3 cok_web.py --account-device --persistent     # 常驻连接(实时, 但 App 会被踢)
```

启动后终端会打印带 token 的地址, 例如
`http://127.0.0.1:8770/?t=NEU_CFJaUCvx-ogmScbHKAnk`
(token 存在同目录 `.cok-web-token`, 首次访问后前端会存进 localStorage)。

| 参数 | 说明 |
|---|---|
| `--host` / `--port` | 监听地址与端口(默认 `127.0.0.1:8770`) |
| `--interval` | 轮询间隔秒(默认 **300**) |
| `--persistent` | 常驻连接; 默认是**按需短连接** |
| `--webhook` / `--webhook-type` | 告警推送(generic / wechat / dingtalk) |
| `--token` / `--no-token` | 访问鉴权(默认自动生成 token) |
| `--open` | 启动后打开浏览器 |

## ⚠️ 与 App 互斥(同账号只允许一个连接)

游戏服**同账号只允许一个连接**, 网页和 App 不能同时在线。
控制台默认走**按需短连接**: 每轮轮询连上 → 拉完数据 → **立刻断开**, 把账号还给 App。

进一步做了**让路检测**: 轮询前先看 App 是否在跑(`adb shell ps -A`),
App 在线就**整轮跳过**, 顶栏显示「App 在线, 已让出账号」。
所以可以边玩边看监控, 代价是 App 在线期间监控数据会滞后。

如果想实时监控而不玩 App, 加 `--persistent`(常驻连接, App 会被一直踢)。

### 账号锁(`cok_client.account_lock`)

同账号只允许一个连接, 所以所有对游戏服的操作都要走同一把锁:

* **跨进程** —— `flock` 跨进程生效, 网页 / 扫描脚本 / 采集脚本互斥
* **进程内可重入** —— 同**线程**嵌套取锁只加计数, 不重新 flock
  (flock 按 fd 生效, 同进程另开一个 fd 去 flock 会和自己冲突)

> ⚠️ **可重入只能按线程判定**(2026-10-25 修)。
> 计数是进程级的, 不分线程的话, 后台轮询线程会误以为自己拿到了独占权,
> 于是**和打怪线程同时连游戏服 → 服务端互踢** → 表现为打怪随机掉线
> (`连接被服务端关闭(已收 0/3 字节)`)。实测掉线间隔不规律(31 秒 ~ 176 秒),
> 一开始怀疑是服务端限流, 实际是自家人打架。
> 现在 `_LOCK_STATE` 里记了持有者的 thread id, 只有同线程才走计数,
> 别的线程老老实实去 flock —— 拿不到就抛 `AccountBusy`, 该轮跳过。

配套的三条:

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面横幅误报「账号正被占用 · 当前持有: 41249 web-action」 | 网页自己的 daemon 持锁, `account_is_busy()` 把它算成外部占用 | `account_holder_info()` 记 holder 的 pid, 和本进程相同就不算 busy |
| 锁文件里留着已经不存在的占用者 | flock 释放了, 但文件里的 `pid purpose` 没清 | 释放时在**解锁之前**清空(注意 `ftruncate` 不重置 fd 偏移量, 要先 `lseek`) |
| 打怪期间顶灯显示「连接异常」 | 「账号正被占用」被写进了 `last_error` | 占用不是故障, 不写 `last_error`; 打怪时顶灯优先显示「自动打怪中」 |

排查这类问题时**先排除自家人打架**, 再怀疑服务端:
`lsof -p <网页PID> | grep cok-account` 看有没有真持有者,
再从外部进程 `flock(LOCK_EX|LOCK_NB)` 探一次 —— 拿得到就是没人真占着。

## 账号从哪来(可以完全不插手机)

账号有两个来源, 按优先级:

| 来源 | 说明 |
|---|---|
| **设备 SharedPreferences** | 最新最准。`cok_account.load_account()` 从 App 的 prefs 读 pfId / gameUid / deviceId / uuid / signCode / buildCode / host / port |
| **内置 ACCOUNT** | `cok_client.ACCOUNT` —— 从线上登录请求复原的凭据。**signCode 是由 APK 签名证书静态派生的**(`md5(hex(java_hashcode(certDER)) + "." + certDER.hex())`), 所以**不依赖设备也能登录** |

2026-10-25 实测: 手机完全没插(adb 扫不到), 用内置凭据直连游戏服
**登录成功**, 7 项监控 + 25 个队列 + 体力全部正常拉到。

设备读不到时页面顶部会显示「当前使用内置凭据」横幅, 数据照常可用;
设备插回来后点一次「立即刷新」会自动优先用设备里的最新账号。

> ⚠️ 设备读账号时 **`load_account()` 不抛异常, 只返回空/残缺 dict**
> (adb 的报错文本里没有 SharedPreferences XML)。
> 所以必须自己校验必需字段, 否则会拿着空账号去连游戏服,
> 报成极具误导性的"连接被服务端关闭"。

> ⚠️ `cok_web.py` 的 `--host/--port` 是**网页监听地址**,
> 游戏服地址用 `--game-host/--game-port`(默认 `txaia-cok.elexapp.com:32231`)。
> 早期两者混用, 导致控制台连自己 —— 设备账号自带 host 才掩盖住这个问题。

| 块 | 显示 | 颜色含义 |

**「今日待办」卡**(操作区第一张, 占满两列)

按**真实状态**汇总今天该做的事, 每条右侧有直达按钮:

* 今日还没签到 → 「去签到」
* 有 N 个任务奖励可领(日常/周/领主) → 「去领取」
* 港口有 N 条船的奖励没领 → 「去领取」
* N 个队列可以加速 → 「去加速」(跳到加速卡)
* 保护罩还剩多久 / 当前没有保护罩 → 「去开罩」
* 体力偏低 → 「看打怪」

已完成的项目用 ✓ 灰色显示, 让人一眼看到"还剩什么"。

**操作区**

* 每日签到 / 领取奖励(带已领记忆与上限, 与 daemon 同一套逻辑)
* **建造 / 训练队列加速**(`queue.ccd`): 选队列 + 选加速道具 + 数量, 或用金币
* **保护罩**(`onekeybuff.use`): 选槽位 + 是否覆盖旧罩; 可开启「被攻击自动开罩」
* **港口**(`newBoat` 族): 船表 + 一键领取 + 一键分派 + 自动开关
* **打野怪**(`autoQueue` 族): 体力剩余 + 野怪等级下拉 + 等级范围 + 部队编成 + 开/停
* **告警**: 选载荷格式、填 URL、发测试

**监控区**(8 张卡, 状态变化才更新)

每日签到 / 周任务 / 可领日常任务 / 领主任务 / 主线任务 / 联盟 Boss / 进行中的队列 / 功能概览

**事件流**: 连接、状态变化、签到、领奖、加速、开罩、告警、异常, 全部实时显示。

## 页面交互约定(2026-10-25 重做)

这一版把三个老毛病一次性解决了, 行为约定如下:

### 1. 设置刷新后不丢 —— 设置存在**后端**

设置落在同目录 `web-settings.json`, **不是**浏览器 localStorage。
所以刷新页面、换浏览器、换电脑都还在。

| 设置项 | 作用 |
|---|---|
| `autoSign` | 每轮轮询顺带签到 |
| `autoShield` | 被攻击自动开罩 |
| `cover` | 开罩时覆盖旧罩 |
| `autoPoll` | 关掉后网页**完全不再连游戏服**, 只等手动「立即刷新」 |
| `hookType` / `hookURL` | 告警载荷格式与地址 |
| `lvLow` / `lvHigh` | 野怪等级范围(服务端是「下限;上限」) |
| `format` / `perType` | 部队编成与每兵种派出数 |
| `huntNum` / `huntMax` | 自建打怪循环的每只兵数与总只数上限 |

写入带**序号守卫**: 前端连续输入会并发 POST, 迟到的旧值不会覆盖新值。
等级范围会**归一化**: 下限调到 4 而上限还是 1 时, 上限自动跟到 4
(不会把你刚输入的值压回去), 页面不会出现 `[4] - [1]` 这种非法区间。

### 2. 按钮点了没反应 —— 三处一起修

* **「立即刷新」原来只读缓存**(按需模式下要等最多 5 分钟)。
  现在后端 `action:"refresh-now"` 会**真的触发一轮轮询**, 点完立刻出数。
* **页面被轮询堵死**: 早先 `_poll_once()` / `action()` 和 `snapshot()`
  共用同一把锁, 而轮询全程持锁做网络 I/O —— 只要有一轮在跑,
  `/api/state` 就整个卡住(最长 60 秒), 页面看着就是「没反应」。
  现在锁拆成两把: `op_lock`(串行化对游戏服的操作) + `lock`(只保护内存, 毫秒级),
  **页面在任何时候都能读**。纯本地动作(保存设置 / 发测试)连 `op_lock` 都不进,
  不会被慢轮询拖住。
* **失败被吞掉**: 按钮统一走 `busy()` 包装(禁用 + spinner + 完成后恢复),
  异常会被转成可见反馈。每个操作区有**持久结果条**(带时间戳, 刷新后仍在),
  校验失败(没选队列 / 没填 URL / 下限大于上限)也写进去, 不只是弹一下就消失的 toast。

### 3. 状态一眼可见

* 顶栏: 连接状态灯 + **最后刷新时间(绝对+相对)** + 服务器日期 + 金币 + 连接模式
* **顶部横幅**: 设备没连上 / 连接异常时, 直接把原因和处理办法摆出来
* 监控卡片空态会说明**为什么没数据**(连接异常 / App 在线让路 / 等待首轮轮询)

### 设备掉线不再要重启控制台

账号来自设备 SharedPreferences。设备拔了线, 控制台**照常启动**:
启动时提示读不到账号, 页面横幅显示「设备未连接」并列出缺哪些字段,
**设备插回来后点一次「立即刷新」就自动恢复**, 不用重启服务。

## 界面体验优化(2026-10-25 第二轮)

第一轮解决的是"能不能用"(设置丢失 / 按钮没反应 / 状态看不见),
这一轮解决的是"用起来顺不顺"。

### 1. 全局概览条 —— 一眼看清现在该做什么

原来打开页面第一眼是**一排操作按钮**, 得自己判断该点哪个。
现在 header 下面是一排概览块(待办 / 签到 / 体力 / 自动打怪 / 港口 / 队列 / 保护罩 / 任务奖励),
每块显示**当前真实数值**并用颜色表达紧急度(黄=要处理, 绿=没问题, 红=积压多)。
点任意一块直接**滚动+高亮**到对应卡片。

### 2. 「今日待办」卡 —— 把散落的事收拢

原来"今天要做什么"要从 8 张监控卡里自己拼(签到状态在第一张、
任务奖励在第三张、港口在操作区)。现在一张卡按真实状态汇总,
每条右侧带**直达按钮**: 「去签到」「去领取」「去加速」「去开罩」「看打怪」。
已完成的项目用 ✓ 置灰, 一眼看到"还剩什么"。

汇总口径:
* 签到: `states.dailySign['今日已签']`
* 任务奖励: 日常(`可领日常任务`) + 周(`周任务可领奖励`) + 领主(`可领奖励`)
* 港口: `dock.rewardable`(只算 `state=3 且 type!=0` 的船)
* 加速: `queues` 里 `running` 的队列数
* 保护罩: `shield.end_ms` 减去当前时间
* 体力: 优先用 `hunter.stamina`(打怪时轮询读不到体力)

### 3. 卡片可折叠 + 状态记忆

页面有 14 张卡, 一屏放不下。现在每张卡右上角有折叠按钮(悬停显示),
折叠状态存 `localStorage` 的 `cokFolded`, **刷新/换浏览器都保留**。
折叠后标题右侧显示**摘要**(如「今日已签」「还剩 5 时 51 分」「4 个进行中」),
不展开也知道大概情况。

监控卡的折叠摘要同样生效, 且**折叠按钮的 ＋/－ 状态会自动同步**。

### 4. 消除闪烁

页面每 5 秒刷新一次, 原来每次都把 8 张监控卡 `innerHTML` 全量重写 ——
用户正要点按钮时卡片就换了。改成**内容签名去重**:
只有关键状态真的变了才重绘, 否则整块不动。

### 5. 事件区可筛选

原来只能看全部。工具条支持: 全部 / 异常 / 警告 / 连接 / 状态,
另有「清空」(只清显示, 后端历史还在)和「高度」(280/420/620 三档循环)。

### 6. 键盘快捷键

|---|---|

## 玩家坐标查询 —— 道具路径(兜底)

输入玩家名字, 查出他在世界地图上的坐标(X / Y)。
**这条路径消耗「坐标侦查」道具**, 现在只作 `world.get` 批量接口失败后的兜底
(见下一节)。首选路线是 `world.get`, 零消耗。

### 协议链路

来源客户端 `game/Spy/PlayerSearchView.lua` + `PlayerSearchListView.lua`:

| 步骤 | 命令 | 说明 |
|---|---|---|
| 1 | `search.player.spy {userName, item}` | 返回候选玩家列表 `[{name, uid}, ...]` |
| 2 | `search.player.spy {userName, item, uid}` | 再发一次, 这次返回带 `location`(**地图点位 index**) |
| 3 | 本地换算 | index → (x, y) |

⚠️ **第 2 步是"选中玩家后用同一个命令再查一次"** —— 第一次只给 uid,
选中后才回 location(客户端 `PlayerSearchListView:getDataCallBack`)。

### 坐标换算

`WorldController::getPointByPoint` 的反函数, 与 `cok_hunt.point_index` 必须互逆:

```
index = x + 1 + int(1201 * y)
x     = (index - 1) % 1201
y     = (index - 1) // 1201
```

世界 x 方向格数 1201 来自 `login.dataconfig` 的 `worldmap_map.k1`。
实现见 `cok_locate.index_to_point` / `cok_hunt.point_index`。

### 侦察道具(item)

| item | 名称 | 用途 |
|---|---|---|
| **212054** | 坐标侦查 | ✅ 目标: 返回 location |
| 212055 | 战争守护侦查 | 返回保护罩信息(不是坐标) |

⚠️ **坐标侦查会消耗道具** —— 这是游戏本身的机制(服务端扣「坐标侦查」道具),
不是网页的限制。

💡 **但现在不需要它了**: `world.get` 批量接口(见下一节)能零消耗拿到坐标,
网页优先走那条路, 道具路径只作最后兜底。

### 实测结论(2026-10-25 区服 2223)

```
search.player.spy {userName:"测试"}                 -> E000000  (item 必填)
search.player.spy {userName:"测试", item:""}        -> E000000
search.player.spy {userName:"测试", item:"0"}       -> E000000
search.player.spy {userName:"测试", item:"1"}       -> E000000
search.player.spy {userName:"测试", item:"212054"}  -> E100165  ← 道具数量不足
search.player.spy {userName:"测试", item:"212055"}  -> E100165
```

**结论: 命令存在、参数被正确识别、只是账号没有「坐标侦查」道具。**
(命令 `search.player.spy` 甚至不在静态反编译出的命令目录里 —— 目录不能当白名单用。)

**错误码语义**(设备 text_zh_CN.ini 实测):

| 错误码 | 含义 |
|---|---|
| `E100165` | **道具数量不足** ← 没有坐标侦查道具 |
| `E000000` | 参数无效(命令名存在, 但参数不对) |
| `E000004` | 无效参数 |
| `E100047` | 体力不足, 不能发起攻击 |
| `102192` | 功能未开启, 敬请期待 |

### 怎么拿到「坐标侦查」道具

* **游戏内**: 背包里点「坐标侦查」道具会直接打开搜索界面
  (客户端 `JumpPageController.lua:165` / `gameCommonFunc.lua:17` 都走这条)
* 配置表里 `ItemSpec id=20024306` → `item=212054`, `price=3000`, `add=150`
  (3000 钻石 / 150 活动积分) —— 属于「道具商店」类商品, 不在 `mall 101/103/106/108/117/127` 这几个通用商城里

## 玩家坐标查询(按名字找人) —— `world.get` 批量接口

### 关键协议(2026-10-25 抓客户端流量得到)

游戏客户端滑动世界地图时用的是 **`world.get`**:

```
world.get { x: INT, y: INT, type: INT, serverId: INT, timeStamp: INT }
```

→ 服务端返回**以 (x,y) 为中心的一整片区域**(实测约 24×24 格)的全部地块,
其中**直接带玩家名和坐标**。

返回结构(实测):

```
{
  timeStamp, x, y, section, serverId, moveCityTime,
  collectLine: [ 行军/采集线 ],
  m:          [ 地图对象 ],
  points:     [ "<JSON 字符串数组>" ]   ← 地块数组, 是**字符串**, 要二次 json.loads

```

`points` 每个地块:

| 字段 | 含义 |
|---|---|
| `i` | 坐标 index |
| `uid` | 玩家 uid |
| `o` | 玩家名字 |
| `t` | 地块类型(实测 1=玩家城, 3=资源点, 9/1003=其他) |
| `l` | 等级 |

### 两个必须注意的坑

1. **参数类型必须显式 INT** —— Python 的 `int` 会被编码成 BYTE(0x02),

   实现见 `cok_map._I()`。
2. **覆盖半径约 24 格** —— 相对中心 x −12~+11, y −13~+11。
   步进必须 ≤ 半径, 否则会漏格子(实现用 `STEP=12`)。

### ⚠️⚠️ 坐标为什么会错: **响应与请求错位**(2026-10-25 定案)

这是 2026-10-25 踩到的最大的坑, **务必先看这段再用坐标**。

**先说结论: 不是导出 bug, 不是解析 bug, 也不是服务端重排地图。**
根因是**响应错位** —— 扫描时拿到的响应属于**别的请求中心**。

**机制(完整链条)**:

1. `cok_client.call` 在**超时后自动重发**同一条命令(`retries=1`)
2. 迟到的旧响应**命令名相同**, 被重发的那次当成自己的响应**认领**
3. 真正的新响应滞留在 socket 缓冲区, 被**下一个**请求读走
4. **错位从此开始并持续传染** —— 之后每个请求都读到上一个请求的响应
5. 于是扫描时中心 (288,840) 的响应里出现了别处玩家的坐标(包括"自己"的 (724,979))
6. 最后覆盖进索引的那个值就是错的 → **91% 的玩家坐标是坏的**,
   而 **9% 恰好是对的**(它们只被覆盖过一次, 没等到第二次覆盖)

**实测证据链(全部可复现)**:

| 检验 | 结果 |
|---|---|
| `world.get` 响应字段 | 含 **x/y 回显**(`_cok_, collectLine, m, moveCityTime, points, section, serverId, timeStamp, x, y`) |
| 真实覆盖区 | 中心 **x −12 ~ +8**(很小) → 索引里远到全图的坐标必然是拿了别的中心 |
| 同一 uid 一次出现次数 | **1 次**(排除"玩家有多个城点") |
| 解码模式 | `mode=val`, 完整消费缓冲区(排除解码错乱) |
| 同中心连查两次 | 结果**完全一致** → 服务端稳定 |
| `res.tile.find`(找最近的怪) 连查 3 次 | 全部贴着玩家真实位置 → **服务端位置数据稳定** |
| 新旧两次全图索引对比 | 91% 坐标变了、9% 没变、**整体分布不变**、错位样本偏移**铺满全图** |

> 我一开始误判成"服务端重排地图" —— 是**用户否定**后才查实的。
> 教训: 「服务端把数据改了」和「我拿错了数据」必须分开验证,
> 手段是**换个不依赖该接口的独立来源交叉验证**(这里用的是 `res.tile.find`)。

**修复(四层, 都在 `cok_map.fetch_area` / `cok_client`)**:

1. `client.call(..., retries=0)` —— **禁用 call 内部自动重发**(错位就是它引起的)
2. 每次重试/异常前先 `client.drain()` 清空 socket —— 不让迟到响应被认领
3. **响应回显校验** —— 响应的 x/y 必须等于请求中心, 不符就丢弃 + 清空 + 重发
4. **越界点过滤 + 众数投票** —— 合并时剔掉离中心过远的点; 坐标取多次观测的
   **众数**而不是"最后一次覆盖"

**页面「查玩家」的实时校验**(2026-10-25 加): 命中本地索引后, 再用一次 `world.get`
(0.17 秒)查那个坐标现在还是不是他:

* 还是他 → 返回**服务端给的最新值**(`source=index+verified`)
* 已经不是他 → 索引坐标作废, 自动降级到**现场扫描**

## ⚠️ SFS 编码的两个坑(2026-10-25 修复)

### 1. 数组 count 必须是 2 字节

`cok_sfs.py` 的编码器原来用 `struct.pack(">I", len(x))`(4 字节),
但**服务端解码用的是 2 字节**(`read_value` 里 `n = r.u16()`)。
→ 凡是带数组参数的命令, 服务端解析时**协议错位**, 表现为「命令无响应 / 超时 30 秒」。

实测修复前后:

| 命令 | 修复前 | 修复后 |
|---|---|---|
| `world.get {points:[...]}` | 30 秒超时 | 0.2 秒返回业务错误码 |
| `get.user.info.multi {uids:[...]}` | 30 秒超时 | 0.2 秒返回 E000000 |

### 2. 整数参数要显式指定类型

Python 的 `int` 会被编码成 **BYTE(0x02)**(0~255) 或 SHORT,
但服务端要 **INT(0x04)**。`world.get` 的 `x/y/type/serverId/timeStamp` 全是 INT,
传普通 int 会回 `E000000`。

```python
from cok_sfs import TypedInt, SFS_INT
params = {"x": TypedInt(531, SFS_INT), "y": TypedInt(931, SFS_INT), ...}
```

`cok_map._I()` 是这个转换的封装。

   200201 的 name = `9200330|9200319` → 模板「{0}加速」+ 填充「5分钟」= **「5分钟加速」**。
   只取第一段会得到「{0}加速」。
2. **两版文本库要合并**, 且**占位符版不覆盖具体版**。
   APK 内置的是旧版(具体值「5分钟加速」), 设备上的 `files/text_zh_CN.ini` 是新版
   (退化成「{0}加速」)。合并规则: 旧版有具体值就保留。
3. **主线任务的 `{0}` 用 `target` 填充**, 不是删掉。
   33101001 = 「城堡升到{0}级」+ target=2 → 「城堡升到2级」。
   删掉会得到读不通的「城堡升到级」; 没有可填值时保留成「?」(如「攻打?次联盟BOSS」)。

### 自动打怪(网页自带循环, 不需要周卡)

网页的「自建自动打怪循环」走的是**手动出征**(`world.march` type=6), 所以
**不需要「自动打怪周卡」, 也不碰服务端那个功能**(页面上已把周卡入口移除)。

### 多队并行

* **并行队伍数**可设 1~8 队(默认 4)
* **每队绑定一个互不相同的兵种** —— 这是判定准确的关键:
  出发时记下该兵种 `army[].march` 的基线, 之后该兵种外勤数回到基线
  就说明这支队回来了。各队兵种不同, 彼此不会干扰。
* **并发数随体力自动收缩**: 体力是**按怪**消耗的(并行 N 队 = N 倍消耗速度),
  而体力恢复只有约 1 点 / 130 秒。所以每派一队前都重新算"体力够不够再派一队",
  体力不够就少派, 不会派出打不动的队。
* **体力不足不算失败**(2026-10-25 修): 服务端回 `E100047` = "体力不足, 不能发起攻击"
  (设备文本表实测)。这是**正常等待**, 不是出错:
  * 不计入 `fails` —— 否则计数全是噪音(修之前出现过 `kills=9 / fails=124`,
    那 124 次"失败"其实只是没体力)
  * **不再白跑找怪** —— 体力不够时直接跳过, 不发 `find_monster` 请求(纯浪费往返)
  * 立刻停止本轮派队, 等下一轮恢复
* 本地体力读数与服务端判断偶尔有出入(本地说够、服务端说不够),
  所以两条路都要拦: 本地预检 + 服务端 `E100047` 兜底。

### 队伍编成(不用手填 id)

「队伍编成」是**下拉选择**: 每队一行 = 兵种下拉 + 数量。
下拉数据来自 `world.user.march`, 带**中文名**和**可用数量**
(中文名从 `id-names.json` 取, 复合名 `{{名|名|...}}` 会清洗成第一个)。

只列**标准兵种**(6 位 `107xxx` 系列) —— 活动限定兵种(8 位 id)不能和普通兵种
混编, 服务端会回 E000000。

编成保存在**后端设置**(`web-settings.json` 的 `squadSpec`),
刷新页面 / 换浏览器都不丢; 同时也会写一份到服务端 `autoQueue.save format`
保持两边一致。

### 页面上的进度

每支队伍一行: 队号 / 兵种 / 数量 / 状态(待命·出征中·已回来) / 目标坐标 / 已打数。
「开始自动打怪」点了以后按钮变成「已开启」并禁用; 没开的时候「停止」置灰。


「自动打怪」这个**服务端功能**(`autoQueue.status {1}`)需要「自动打怪周卡」
(道具 `771836`, 状态 id `22604360`), 没周卡时服务端返回 **E000000**。
**但手动出征同样扣体力**, 所以网页自己做循环即可, 不受周卡限制:

```
找怪(res.tile.find) → 换算 index → 算 marchKey → 出征(world.march) → 等结算 → 下一只
```

`AutoHunter` 实现在 `cok_hunt.py`, 网页上点「开始自动打怪」即启动(用一条**常驻连接**,
App 会被踢下线; 写操作有二次确认)。

> **⚠️ 开自动打怪会自动 `am force-stop` 掉 App**。因为游戏服**同账号只允许一个连接**,
> App 占着账号时网页连上去会被服务端主动断开 —— 表现成"命令不被接受", 其实是互踢。
> 这个坑排查过一次, 任何"连接被服务端关闭"都该先排除它。

**坐标换算(静态反汇编得出, 已用服务端回显验证)**:
`libgame.so` 里 `WorldController::getIndexByPoint`(device 版 `0xecb8d8`):

```
index = (uint)point.x + 1 + (uint)((float)w1 * point.y)     // w1 = 1201
```

即 **`index = y*1201 + x + 1`**(y 是主维度)。
**验证**: 找 1 级怪得坐标 (504,915) → 算得 index `1099420` → 出征后服务端回显
`"dp": 1099420`, 完全一致。**marchKey 错则服务端回 E000000, 对则出征成功** ——
所以 marchKey 也是服务端校验的。

**marchKey 算法**(客户端 `AutoQueueInfo:autoMarch`):
`md5( index + "1021" + (type+1)*1000 + [兵种id, speed, load, 数量]* + 盐 )`
多兵种时拼接顺序取决于客户端 `ipairs4ScatteredT`(C++ 散列表遍历序), 未确定 ——
所以实现**只用单兵种**(顺序唯一, 可复现)。`speed`/`load` 取自 `world.user.march`。

**⚠️ `soldiers` 的数量必须显式编码成 SFS INT** —— 通用编码会把普通 Python int
压成 BYTE(0x02), 服务端回 E000000。key 是字符串(客户端 CCDictionary key 必为 string)。

**⚠️ 编成里不能混活动限定兵种**: `575xxxxx` / `40400xxx` 这类 8 位 id 与普通兵种(6 位 `107xxx`)
混编时服务端回 E000000(单独一个 575 兵种可以)。页面的「按可用兵自动编成」只挑标准兵种。

**体力实测数据(2026-10-24)**:
* 每打一只野怪扣 **9** 点体力(113→104, 108→99)
* 体力**不靠战斗胜利返还**, 只随时间恢复, 约 **1 点 / 130 秒**
* 所以满体力 100 大约能打 **11 只**, 打完约需 20 分钟回满
* 服务端 `stamina` 实测最高到 **113**(超过 100, 可能有加成), 客户端主世界配置里
  **没有** `staminaMax`(`login.dataconfig` 的 319 张表里它只出现在中立/帝国战场),
  所以代码里 `STAMINA_MAX=100` 是保守值, 可用环境变量 `COK_STAMINA_MAX` 覆盖

**循环判据(实测)**: 战斗结算的 push 不稳定收到(有时是
`push.general.awake.challenge.monster.lose` 这种名字), 所以**不靠 push**,
而是轮询 `world.user.march` 的 `army[].march` —— 部队在外时该值 > 0, 回来了就归零。

**端到端实测通过**:
* 直连跑 `AutoHunter`(1 级怪 / 1 兵 / 最多 2 只): 打了 2 只, 0 失败,
  中间正确出现「等部队回来(还有 1 在外)」→ `troops_out` 1→0 → 再打下一只
* 网页点「开始自动打怪」: `kills:1, fails:0`, 目标怪 (545,940) → index 1129486

**找怪只查坐标(不扣体力, 每天搜索次数有限, 实测 `maxSearchCount=6`)**。

### 被攻击自动开罩

触发信号是**服务端推送**(`push.world.injured` / `push.world.cannon.injured` /
`push.world.march.fail`)。而推送只在「等待命令响应」期间才会被收到 ——
按需短连接模式下轮完就断开, **永远收不到被攻击, 自动开罩形同虚设**。

所以开启「被攻击自动开罩」时, 网页会**自动切到常驻连接**(顶栏会显示
「常驻连接(App 会被踢)」)。这是收推送的必要代价, 页面有明确提示。

判定逻辑(与 daemon 一致):
* **有罩且未过期** → 不重复开(否则连续被攻击会瞬间烧光道具)
* **被攻击**(force 触发) → 允许续罩
* 冷却期(默认 600 秒)内不再开
* 服务端自带冷却, 冷却期内再开会被拒(文本 105163/105164)

## 港口(码头航海贸易 / newBoat)

### ⚠️ 命令族更正(2026-10-25 实测)

APK 里有**三套并行**的航海贸易命令族, Lua 注释都写"码头航海贸易", 但**只有一套在本区服是开着的**:

| 命令族 | 客户端 Lua | 实测结果 |
|---|---|---|
| **`newBoat.*`** | `game/NewNavigation/NewNavigationCtl.lua` | ✅ **可用**, 返回真实船表 |
| `dockTrade.*` | `game/SeaTrade/SeaTradeCtl.lua` | ❌ `errorCode=102192` |
| `nightCityDock.*` | `game/NightCity/control/NCTradeController.lua` | ❌ `errorCode=102192` |

之前"102192 = 功能未开启"的结论**是接错了命令族**。
`cok_dock.py` 现在会**自动探测**: 依次试 `newBoat` → `dockTrade` → `nightCityDock`,
取第一个服务端真正放行的; 探测到的族名会在页面上显示(「命令族 newBoat」)。

### newBoat 命令族

| 命令 | 参数 | 说明 |
|---|---|---|
| `newBoat.data` | 无 | 港口数据(ships 数组 + shipLimit) |
| `newBoat.oneKeySendShip` | 无 | **一键派遣**(所有空闲船) |
| `newBoat.oneKeyShipReward` | 无 | **一键领取**(所有可领奖的船) |
| `newBoat.sendShip` / `recallShip` / `speedUp` / `shipReward` | `{uuid}` | 单条操作 |

船只状态(`NewNavigationCtl.SHIPSTATE`, 与 `SeaTradeCtl` 一致):

| 值 | 含义 |
|---|---|
| 0 | 未解锁 |
| 1 | **空闲**(可以分派出海) |
| 2 | 贸易中(在途) |
| 3 | **可领奖** ← 定时检查就看这个 |

### 船只字段与 `type` 的含义

`newBoat.data` 实测每条船:

```
uuid / configId / itemId / count / cTime / endTime /
state / speedLimit / speedTimes / type
```

`type` **不是**货物类别, 而是**界面主题**(白天/夜晚, 见 `NewNavigationView.lua`),
但客户端用 `type != "0"` 来判定"这艘船算不算真船":

```lua
if v.type ~= "0" and tonumber(v.state) == SHIPSTATE.FREE then ... end
if v.type ~= "0" and tonumber(v.state) == SHIPSTATE.REWARD then ... end
```

所以 `type=0` 是**空船**(没装货), 客户端不会把它算进可派遣/可领奖。
`cok_dock` 因此把 `type=0` 的船排除在 `idle` / `rewardable` 之外 ——
否则页面会显示"有空闲船可派", 但点了服务端什么都不做。

### 定时检查

* 每轮轮询(默认 5 分钟)读一次港口数据
* 「可领时自动领」→ 有 `state=3 且 type!=0` 的船就一键领
* 「空闲时自动派」→ 有 `state=1 且 type!=0` 的船就一键派
* 两个开关**默认都关**, 因为一键分派会**真的派出船只**(消耗载货/资源)
* **打怪的时候也能检查**: 港口检查会**搭打怪那条连接**(同一线程、同一 socket),
  不额外开连接, 也就不会跟自动打怪互踢

### 领取结果怎么展示

一键领取**不能只说成功/失败**, 要说清**领到了什么、哪些没领到**(用户明确要求):

* 领取**前**先记下当时哪些船是"可领奖"(state=3)
* 调一键领取 → 响应 `array[i].goodsObj.{itemId, addNum, uuid}`
  (客户端读的就是这些字段, 见 `NewNavigationCtl:mergeReward`)
* 领取**后**重新读港口数据, 对比出**仍然是可领奖**的船 = 没领到的
* 页面同时给三样:
  * 结果条: `已领取 N 条` / `仍有 N 条未领取` / `领取失败: <中文原因>`
  * 卡片里的「上次领取」明细区: 逐条 `领到: 5分钟加速 ×1200` + `未领取: <船>`
  * 船表里 state=3 的行直接标 **(未领取)**
* **这份明细会持久保留**: 轮询/自动检查/手动刷新都不会把它冲掉
  (`Engine._set_dock_state` 统一处理)
* 错误码会用 `id-names.json` 的 `reward_names` 翻译成中文
  (如 `102192` → `功能未开启，敬请期待`)

  #4 state=2 type=3 引路虫·幻化 ×15            贸易中
newBoat.oneKeyShipReward → array: []          (当时无可领奖的船)

载货道具的中文名来自 `id-names.json` 的 `item_names`(例如 `36008371` → `25金币`)。

所以货物种类名取不到, 但**道具名**能取到。



## 背包(道具实例 uuid / 数量)

加速要的是**道具实例 uuid**(`queue.ccd` 的 `itemUUID`), 不是配置 id。

**数据源**: `bag-items.json` —— 由 `dump_bag.py` 采集:
客户端的道具数据在 C++ `ToolController` 里
(`getToolIdsByType(type)` 列出道具 id, `getToolInfoByIdForLua(id)` → `uuid` / `getCNT()`),
所以用 **frida attach 到 App 并注入一段 Lua** 就能读出来, 不需要猜协议命令。

```bash
# 手机上打开游戏(进主城即可, 不必点背包), 然后:
python3 dump_bag.py --launch --out bag-items.json --speedup speedup-owned.json
```

* `--launch`: App 没开时自动拉起
* 需要设备已 root 且 `/data/local/tmp/frida-server` 在跑
* **同账号只允许一个连接** —— 采集期间网页控制台要停着(App 也会被顶掉)

**已确认的事实**:
* 背包的**字段名是 `useritemlist`**(不是 "items"), 每条带 `uuid`。
  静态定位: `libgame.so` 字符串表 0x2fde030; 解析函数 `0xfd9498`
  (从消息 `params` 取 `useritemlist` 逐条入 ToolController);
  相关 `ToolController::initGoodsGroup` 在 0xfc9700
* **`push.item.having` 是增量通知**, 不是全量 ——
  它的处理函数(0xb833b8)日志是 `"SendItemPush - get a item(%d) from(%s)."`
* **init push 里没有背包**: 把 `rlQW45Y` 嵌套结构全量递归扫过,
  带 uuid 的 dict 只有 101 个, 全是 `building[]`(建筑实例), 没有 itemId
* **`cemetery.get.info` 不是背包** —— 它返回英灵殿(`kingdomCemetery`/`userCemetery`/`beforeDead`…)
* `show.status.item` 是 **buff 状态**(`statusItems`); `itemcollection.data` 是**收藏**
* ⚠️ **"直连某命令被服务端踢连接" 的第一嫌疑不是协议, 是同账号双连接互踢** ——
  先 `am force-stop` 掉 App 再测, 否则会把互踢误判成"命令不被接受"
* ⚠️ **服务端会丢弃新连接的首条业务请求**, 必须重发一次才有响应。
  扫描命令时用 `retries=0` 会**全部超时**, 结论无效
* ⚠️⚠️ **地图坐标是快照, 服务端会重排整张地图** —— 扫完的索引过一段时间
  坐标会**整体作废**(原位置换成别人)。详见上面「坐标是快照」那节
* ⚠️ **"查不到某个玩家" 先怀疑索引过期, 再怀疑协议** —— 用一次 `world.get`
  查查那个坐标现在站着谁, 一步就能定性

**当前结论**: 直连拉全背包的命令名**仍未定位**(2026-10-25)。
所以背包数据目前仍来自 `dump_bag.py`(需要手机 + frida + root)。
页面上的「背包数据来源」会明确标出这是快照还是实时, 不会让你误以为是实时值。

排查用的工具(都在本目录, 都不需要设备):

```bash
python3 dump_init_push.py --out init.jsonl --find-items   # 抓 init push 找背包
python3 probe_bag_cmd2.py                                  # 试候选命令(每条重连)
python3 sweep_bag.py --all                                 # 全量扫客户端命令
```

**元数据**(`speedup-meta.json`, 471 条) 来自 `speedup-items.json` 的分组:
`seconds`(时长秒) / `type2`(ItemSpdMenu 索引) / `label`(适用场景)。

## 安全

* 默认只绑 `127.0.0.1`, 且带随机 token(`--no-token` 可关, 仅建议本机用)
* 所有写操作(签到/领奖/加速/开罩/自动打怪)前端都带**二次确认**弹窗
* 背包读取是只读的(读 App 内存), 但需要 frida + root
